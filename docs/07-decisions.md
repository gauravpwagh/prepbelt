# PrepBelt — Implementation Decisions

Decisions taken while building, where the specs were silent, ambiguous or in conflict. Each one names who decided. Specs `01`–`06` remain the source of truth; this file only fills gaps.

| # | Topic | Decision | Decided by |
| --- | --- | --- | --- |
| D1 | Toolchain | Stay on the installed Flutter 3.41.6 / Dart 3.11. Packages are pinned to the newest stable releases that support it: Riverpod 3.2.1 (riverpod_generator 4.0.3), drift 2.31.0 (spec table: 2.32.0), drift_flutter 0.2.0, go_router 17.5.0 (spec: 17.1.0), freezed 3.2.5, json_serializable 6.13.0. These are the only releases whose code generators share an analyzer version (9.x). Upgrade together when moving to Flutter 3.44+. | Owner, 28 Oct 2026 |
| D2 | Promotion | ~~Level follows stability: after the first review (always level 1), `levelAfter = levelFor(S)`, up or down. With all-Good ratings and default FSRS a task goes 1 → 3 → 5 → 6 → 7, reaching Black at the 5th review (about day 163). An optional cap, `review.maxPromotionPerReview`, limits the levels gained per review; it is off by default. (First chosen as "+1 per review"; reversed after it put Black about 3.5 years away.)~~ Superseded by D20: level now rises one belt per Good review. | Owner, 28 Oct 2026 |
| D3 | Stripes | ~~Shine R maps to stripes: R ≥ 0.90 → 2 stripes, 0.80 ≤ R < 0.90 → 1 stripe, below 0.80 → no stripes. R < 0.70 and overdue → displayed level drops one and the belt is drawn faded. Cut-offs are in configuration.~~ Superseded by D20: stripes now show dim steps, not recall. | Owner, 28 Oct 2026 |
| D4 | Pauses in rebuild | `rebuild(reviews, pauses)` takes pause intervals as well as reviews. The intervals come from the task's pause and resume Events, skipping undone events, so a rebuilt TaskState equals the incremental one. | Owner, 28 Oct 2026 |
| D5 | Engine imports | `CLAUDE.md` says engines depend only on Dart and `core/time`; `05-architecture.md` also allows `core/config`. Engines import `core/time` and `core/config` (both pure Dart) and nothing else from the app. The CI check enforces that list. | Claude, following the more specific spec |
| D6 | Pause | Paused tasks do not dim and have nothing due. On resume, `lastReviewAt` moves later by the paused duration and the schedule re-fits from there: without an exam the due date moves by exactly the paused time; with one, the remaining reviews re-fit before it. Review rows keep their real times. (Updated for D20.) | Claude |
| D7 | FSRS setup | ~~`FsrsScheduler` uses no learning or relearning steps (study sessions are at most daily) and no interval fuzzing (rebuild must be deterministic). Forgot therefore schedules the next review from the new, lower stability, at least 1 day out ("back tomorrow").~~ Superseded by D20: FSRS removed. | Claude |
| D8 | Event payload | One Event per operation. Its payload lists every row the operation changed: `{"changes": [{"table", "id", "before", "after"}]}`. `entity`/`entityId` name the aggregate (task, source, exam, setting). Undo applies the `before` values of the latest not-yet-undone event for that entity, in a new transaction that logs its own Event with `undoOf`. Repeated undo walks further back. | Claude |
| D9 | Undoing reviews | Reviews are append-only, so a review Event cannot be undone. Undo on an entity whose latest event is a review fails with a clear error. | Claude |
| D10 | Fonts | Bricolage Grotesque and Manrope are bundled as assets (OFL), not fetched by `google_fonts` at runtime, because phase 1 makes no network calls. | Claude |
| D11 | Weekdays | `Availability.weekday` 0 = Monday … 6 = Sunday (ISO order, `DateTime.weekday - 1`). The data model says only "0–6". | Claude |
| D12 | Calendar dates | Exam day, plan day, override day, quest day and rest-token day are `YYYY-MM-DD` text in the student's local calendar. Instants stay UTC milliseconds. | Claude |
| D13 | Extra columns and index | `PlanItem.order` (the planner spec's "order within the day", missing from the data-model table) and an `Event(entity, entityId)` index for undo lookups. | Claude |
| D14 | Tab routes | `/exams` and `/progress` added for the Exams and Progress tabs, which the architecture route list leaves out. The first-launch redirect to `/onboarding` waits for milestone 6; until then the app opens on Today. | Claude |
| D15 | Level number on badges | `BeltBadge` draws the level number on the knot, so colour is never the only signal even at 0 stripes. The mockups show no number. Brown and Black belts get light stripes, White (light mode) and Black (dark mode) an outline. | Claude |
| D16 | Review config source | `ReviewRepository` reads Setting rows directly for each operation, not through a provider: Riverpod 3 pauses unlistened providers. | Claude |
| D17 | Goldens | Golden images are recorded on Windows, so CI compares them on a Windows runner; Linux CI runs everything else. | Claude |
| D18 | App icon | The owner chose the checkmark ring (`design/brand/4-ring/`) after declining two rounds of belt marks. This waives the CLAUDE.md rules that the icon is a martial-arts belt and uses 2–3 token colours. Android adaptive layers scale the mark to 0.8 for margin inside round masks; the monochrome layer serves Android 13+ themed icons. | Owner, 28 Oct 2026 |
| D19 | App id | `io.github.gauravpwagh.prepbelt` on Android (applicationId, namespace) and iOS (bundle id), derived from the GitHub repo `gauravpwagh/prepbelt`. Replaces the kickoff default `app.prepbelt`. The Dart package stays `prepbelt`. | Owner, 28 Oct 2026 |
| D20 | Review model | FSRS is removed. First read earns White; then 5 scheduled reviews with gaps in proportion 1 : 2 : 3 : 5 : 8, re-fitted after each review to end by the day before the exam (without an exam: 1, 3, 7, 14, 30 days). Good or Easy earns the next belt (5 → Brown); Black needs one more review by choice. Forgot or Hard keeps the belt, dims it one step and repeats the step after 1 day. Belts also dim once overdue and every 2 days after; a Good review restores them; the stored level never drops. Any task may be reviewed early and it counts as its next step. Specs 01–06 and CLAUDE.md are updated to match. | Owner, 28 Oct 2026 |
| D21 | Schema v1 edited in place | TaskState drops the FSRS columns for `step` and `dim`; Review replaces `stabilityAfter` with `stepAfter`, and `dueAfter` becomes nullable. 1.0 has not shipped, so v1 was changed and its snapshot regenerated instead of adding a migration. | Claude |
| D22 | Targets set reviews | A task's belt target in the exam sets how many reviews are planned: one per belt above White, at most 5, at least 1 (High → Black 5, Medium → Blue 4, Low → Green 3; no target 5). Reviews by choice after the plan still earn belts. `plannedReviewsFor(targetLevel)` in the review engine. | Owner, 28 Oct 2026 |
| D23 | pdfrx version | pdfrx 2.4.7 (pdfrx_engine 0.4.5): 2.4.8 needs a newer `meta` than Flutter 3.41 pins. `loadOutline()` verified on the Android emulator by an integration test. | Claude |
| D24 | Survey behaviour | An unsurveyed chapter starts with the answers just given on the previous one (else Medium, Medium, New); answers save on Next. "Mark the other N as Medium" sets Medium importance, Medium difficulty and New familiarity on every unsurveyed chapter, as one undoable step. The 1.2 "others said" hint and 1.1 "from template" tag are not shown yet. Without an exam the importance row and target belt are hidden. | Claude |
| D25 | Screens and enums | Screens may import `core/db/enums.dart` (plain values); the rest of `core/db` stays off-limits to `features/*/ui`. | Claude |
| D26 | Survey covers chapters | The survey asks per top-level chapter; nested parts from PDF bookmarks are stored as child chunks but not surveyed separately. | Claude |
| D27 | Reading as you go | The survey is optional. Tasks come from three routes that can be mixed: the survey, "Add task" on a chapter, and reading a source as you go (`design/notes/source-chapters.md`). A reading sitting is a `ReadingSession` row; on return the student says how far they got and how long it took. Whole chapters read become one task with a firstRead Review whose duration is the time spent on them, across sittings; a partly read chapter waits. A task may cover several consecutive chapters. The planner gets an `explore` PlanItem per source for the part not yet read or tasked (`PlanItem.taskId` becomes nullable, `sourceId` added). Schema v1 is edited in place again, as in D21. | Owner, 28 Oct 2026 |
| D28 | Reading position | Derived, not stored: the explored units are the union of saved ReadingSession ranges and the chunks of tasks that have a firstRead Review; the position is the first unit not in that union. Time on a chapter is apportioned from each sitting by pages (sitting minutes × overlap ÷ sitting pages). Chunks have no topic in 1.0, so a sitting's chapters always form one task; per-topic splitting waits for topic mapping. | Claude |
| D29 | Task now, read later | "Make it a task now" for a partly read chapter, and "Add task" with "Not yet", create a level-0 task for the whole chapter. Its first read is recorded when a later sitting finishes the chapter, with the time from all sittings. Undoing an operation that recorded a first read removes that Review with the task it created; this is the one case where a Review row is soft-deleted, since the task goes with it. | Claude |
| D30 | Pace for the guess | Until the planner's per-subject calibration exists, the "Up to page" guess uses the median minutes per unit of the last 10 saved sittings of the same unit type, blended 50/50 with the default for 3 to 9 sittings (the spec's calibration rule, keyed by unit type). | Claude |
| D31 | Opening sources | `open_filex` 4.7.0 opens stored files and `url_launcher` opens links, as `05-architecture.md` lists. Neither can pass a page number, so the sheet names the page to go to. | Claude |
| D32 | Share into the app | `receive_sharing_intent` 1.9.0 is vendored in `third_party/receive_sharing_intent/` with three Android patches (`PATCHES.md`): copy every shared `content://` file into the cache (upstream returned unreadable storage paths for files shared from the Files app), turn a failed copy into an empty path instead of a crash, and apply Kotlin itself (Flutter 3.41, D1). Android takes `application/pdf` and `text/plain`; the first web link in shared text becomes a Link source, and the text around it its title. Shared links preselect Link, as the Add source note says, even for YouTube. iOS files are in place, but the Share Extension target must be added in Xcode on a Mac (`ios/Share Extension/README.md`). | Claude |
| D33 | Today before the planner | Until the planner (milestone 5) writes PlanItems, Today lists every review due by the end of today, overdue first (oldest first), then at most `todayFirstReadsWithoutPlan` (2) not-started tasks as first reads, High importance first. Review length follows the planner spec (35% then 20% of the first read, 5–30 min). The exam card shows name, date and days to go; exam belt and readiness join it with the planner. | Claude, 29 Oct 2026 |
| D34 | Back from source | Start writes ActiveSession, opens the source, and shows Back from source at once; `SourceReturn` brings it back on resume or cold start, before an open reading sitting. A review and a reading sitting never run together. Rating previews each outcome with the review engine; Done records it (first read for a level-0 task, any rating earns White). Stopping short of the range end saves the page, and the next session resumes there. Close leaves without recording. Minutes are capped at `reading.maxAwayMinutes`. ActiveSession is local, so it is written directly inside the repository transaction and its Event records the action. | Claude, 29 Oct 2026 |
| D35 | Daily reminder | `flutter_local_notifications` 22.3.2 with inexact alarms (no exact-alarm permission). Permission is asked once, after the first finished session, not at launch. Reminders are scheduled 7 days ahead at `ui.reminderTime` (default 19:00); today's is skipped once a review is in; `ui.reminderEnabled` false cancels them. Settings will expose time and on/off in milestone 6. | Claude, 29 Oct 2026 |
| D36 | Task detail design | Built from `design/notes/task-detail.md` without a separate approval round, on the owner's instruction of 29 Oct 2026 to proceed unless a decision is substantial and irreversible. The Redefine menu stays hidden until milestone 6. | Owner, 29 Oct 2026 |
| D37 | Planner, first version | `lib/engines/planner/planner.dart` plans day by day: overdue and due reviews first (carry when full), then first reads in 45-minute sessions, one a day per task, 15-minute floor, one 10-minute overrun, earliest deadline then importance then Hard then source order, 2 per subject a day. Reviews after a first read come from the review engine as if rated Good; the final review lands the day before the exam; the 2-day taper is reviews only. A first read's deadline is the exam minus the sum of its planned gap weights in days (the spec gives no formula). Smoothing pulls a review up to 2 days early only when its own day is over its minutes. Until first launch asks (milestone 6), every day has 90 minutes. Plans are a cache: each run replaces planned rows from today, marks missed ones `moved`, keeps done ones, and logs one Event. It runs on the main isolate for now; an isolate is a performance-pass item. Triage cuts (steps 1–5) are not built yet; the planner reports late High tasks and unplaced minutes. | Claude, 29 Oct 2026 |
| D38 | Add exam and the Exam screen | Add exam (`design/notes/add-exam.md`, built under D36) creates the exam, links every active task as Medium (target Blue) and sets the same daily minutes on all 7 weekdays, in one undoable operation; then the planner runs. The Exams tab shows the exam or an empty state. The Exam screen follows mockup 4 with the 1.0 activity grid (12 weeks, 5 Night-to-sun intensities) in place of the 1.1 mastery timeline. Exam tier, projected tier, readiness and weak links follow `02-data-model.md` literally: attainment is level ÷ effective target, so a syllabus that reaches its targets shows a Black exam belt. If not everything fits, the screen says so; triage cuts are still to build. Flutter's text-contrast check misreads filled text fields (fill against border), so the Add exam guideline test skips it. | Claude, 29 Oct 2026 |
| D39 | Triage, and migrations from v2 | Triage (`lib/engines/planner/triage.dart`) runs the spec's steps 1–4 in order, each on every eligible task at once, and keeps a step only if it brings the plan closer to fitting, so nothing is cut for no gain. A cut is a review limit: the task's reviews keep the dates fitted for its full target and the last ones are dropped, which frees the crowded days before the exam (re-fitting fewer reviews would move the new last one there again). High tasks and tasks the student keeps are never cut. If steps 1–4 are not enough, step 5 offers the extra minutes a day that fit the reduced plan and the whole plan (binary search), dropping tasks one at a time, or accepting a lower belt. Keep previews what would be cut instead before confirming. Choices are ExamTask `triageKeep` and `dropped`, undoable. While fixing a never-fitting plan, final reviews now spread over their windows (High 1–3, Medium 2–5, Low 3–7 days before the exam) instead of all landing on the last day. The new columns are schema v2 with a real migration: there are installs with data now, so in-place edits (D21) end at v1. | Claude, 29 Oct 2026 |
